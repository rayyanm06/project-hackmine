# Smart Resort 360 — System Failure Root Cause Audit

## 1. Executive Summary
The system is experiencing catastrophic data loss and runtime failures primarily due to a severe architectural flaw: the test suite (`test_step11.py` and others) destructively drops all tables in the production SQLite database (`app.db`) when run. This leaves the running backend serving empty tables. Secondary issues include missing frontend event handlers and unenforced SQLite foreign keys that allow corrupt data states.

## 2. Running Processes
- **Python Backend**: PID 12176 is running `uvicorn backend.main:app` on port 8000.
- **Node Frontend**: Multiple `node.exe` processes (e.g., PID 24160) are running `npm run dev` for Vite on port 5173.
- The processes are active, but the backend is serving an empty database.

## 3. Database Path & State
- **Path**: `C:\project\smart_resort\backend\app.db`
- **Size**: ~140 KB
- **State**: The database tables exist but are essentially empty (Users: 0, Staff: 0, Rooms: 0, Tasks: 0). The database was wiped by the `test_db` fixture in the `pytest` suite, which executes `Base.metadata.drop_all()` against the production database path.

## 5. Frontend API Configuration
- Base URL is set to `http://localhost:8000` via `import.meta.env.VITE_API_BASE_URL` fallback in `frontend/src/lib/api.ts`.
- The frontend is correctly connected to the backend, but the backend is returning empty arrays.

## 6. CORS
- Configured in `main.py` to allow `http://localhost:5173` and `http://127.0.0.1:5173`.
- CORS is functioning correctly; the failures are data-driven, not network-blocked.

## 7. Complaint Submission Failure
- **Root Cause**: When a complaint is submitted, the frontend defaults to `guest_id=2`. Because the `User` table was wiped, this guest does not exist.
- **Secondary Issue**: SQLite does not enforce foreign keys by default, so the API returns 200 and creates a floating `Complaint` record, but downstream AI/assignment services fail when they cannot find the associated room/guest/staff data.

## 8. Report Download Failure
- **Root Cause**: The "Download Report" button in `_layout.index.tsx` (Line 27) is a dummy UI element (`<Button variant="outline">Download Report</Button>`). It lacks an `onClick` handler and there is no corresponding backend endpoint to generate a report.

## 9. Staff Failure
- **Root Cause**: The `Staff` and `User` tables were wiped by the test suite. `GET /api/staff` returns `[]`. The frontend receives an empty array and renders a blank page.

## 10. Pricing Failure
- **Root Cause**: The `Competitor` table was wiped. The `pricing_service` explicitly raises a 404 error ("No competitor data found.") when it cannot find market baselines in the DB.

## 11. Audit Trail Failure
- **Root Cause**: The audit log table was wiped. The only visible events are those generated by background tasks (e.g., `next_best_action_generated`) that fired *after* the test suite dropped the tables.

## 12. Recommendations / Room Data
- **Root Cause**: The `Room` table was wiped. The Room Matchmaker filters the database for available rooms, finds 0, and either returns an empty list or fails to generate a meaningful recommendation.

## 13. Seed System
- The seeding mechanism is split: `main.py` seeds rooms on startup, while `seed_data.py` seeds users/staff/complaints manually.
- Because the backend process (PID 12176) was never restarted after the tests wiped the database, `main.py` did not re-seed the rooms. `seed_data.py` was also never re-run.

## 14. Environment / API Keys
- `OPENAI_API_KEY` is utilized by the services but is injected via the environment (not hardcoded).
- No API keys are leaked or improperly exposed in the codebase.

## 16. Current Data Science
- The application currently uses zero authentic Data Science or Machine Learning.
- It relies entirely on basic deterministic heuristics (e.g., counting complaints in a 24h window) and LLM wrappers for Natural Language Generation (NLG).

## 17. In-House ML Opportunities
1. **Complaint Classification**: (TF-IDF + Logistic Regression) replacing the expensive LLM call for routing tickets.
2. **Task SLA Prediction**: (Gradient Boosting / XGBoost) predicting whether a task will breach its time-to-resolve SLA based on staff workload and priority.
3. **Demand Forecasting**: (ARIMA or Prophet) predicting room occupancy to inform the Pricing Intelligence deterministically rather than via LLM.

## 18. External Hotel Data / APIs
- A search for `AMADEUS`, `BOOKING`, and `HOTELBEDS` yielded **no results**.
- There is no real-world hotel identity, PMS integration, or external API configured. The project is entirely isolated and synthetic.

## 19. Public Datasets
- The **Hotel Booking Demand** dataset (Antonio, Almeida, and Nunes) is highly suitable.
- It contains ~119,000 observations (resort and city hotels) with features like lead time, stays, guests, and ADR (Average Daily Rate). This can directly power our Demand Forecasting and Pricing ML models.

## 20. Browser Errors
- The browser fails silently on empty arrays (Staff, Tasks, Rooms).
- Pricing throws a 404 API error mapped to the UI.
- Report Download does absolutely nothing (no network request).

## 21. Root Causes
- **CRITICAL**: The `test_db` fixture in `test_step11.py` (and others) executes `Base.metadata.drop_all(bind=engine)` against the production SQLite database (`backend/app.db`), wiping all data when tests run.
- **HIGH**: SQLite does not enforce foreign keys by default, allowing corrupt, floating records (like a complaint assigned to a non-existent guest).
- **MEDIUM**: The "Download Report" feature is a dummy button with no event handler or backend route.
- **LOW**: Disjointed seeding logic (rooms seeded on startup, users seeded manually) prevents the app from auto-recovering gracefully.

## 22. Recommended Fix Order
1. **Fix Test Suite**: Modify `backend/conftest.py` or the test fixtures to use an in-memory SQLite database (`sqlite:///:memory:`) for tests.
2. **Restore Database**: Run `seed_data.py` and restart the Uvicorn backend process to rebuild the `app.db`.
3. **Enforce Foreign Keys**: Add SQLite PRAGMA `foreign_keys=ON` to the SQLAlchemy engine configuration in `database.py`.
4. **Implement Report API**: Create a `/api/reports` endpoint and wire it to the frontend button.

## 23. Proposed Data Science Architecture
- **Pipeline**: Raw Dataset (e.g., Hotel Booking Demand) → Scikit-Learn Pipeline (Feature Engineering) → Model Training (Logistic Regression/XGBoost) → Pickled Model.
- **Serving**: FastAPI loads the pickled model at startup and provides synchronous `/predict` endpoints.
- **Auditability**: The model's predictions, version, and confidence score MUST be explicitly saved in the `AuditLog` table and displayed on the Audit page, moving away from black-box LLM decisions toward transparent ML governance.

## Final Decision
The current architecture is **salvageable**. The catastrophic failures are entirely due to a configuration/testing flaw rather than a fundamental design limitation. The UI and API contracts are solid. 

**Immediate Action Required**: We MUST fix the test suite to stop dropping the production database, and re-seed the system. Once stabilized, the application is perfectly positioned to replace its LLM wrappers with the proposed In-House ML pipelines.
